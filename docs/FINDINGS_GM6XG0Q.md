# 蛟龙16QS (GM6XG0Q) 适配与实测记录

本文件记录在**机械革命 蛟龙16QS** 上适配本项目时发现的新事实。
结论均在本机实测，与上游 [`docs/FINDINGS.md`](FINDINGS.md)（实测于无界15X）互补；
两处不一致的地方已明确标注。

| 主板 | MECHREVO / GM6XG0Q |

与上游结论一致。

### 只读初始快照

| 寄存器 | 值 | 含义 |
|---|---|---|
| `0x0770` | `0xFF` | ROM ID 出厂空槽 |
| `0x07C3` | `0x07` | 平台值，不等于 4/5 → 门控条件不成立 |
| `0x07A6` | `0x20` | 官方档位 bits[5:4]=2（工作站） |
| `0x07B9` | `0x00` | 未设上限 |
| `0x0742` | `0x02` | bit2=0，门控未开 |
| `0x087F` | 盲区 | H2RAM 通道读不到，恒读 `0xFF` |

与无界15X 的"未修复"特征完全一致 —— 但**下面的差异让诊断一度走偏**。

## 1. 关键差异：`0x0742` bit2 **不反映"存储维持"路径**

上游 `FINDINGS.md` 把 `0x0742` bit2 描述为「限充门控/控制环路激活」，
并把它当作**唯一可靠的效果判据**。**在蛟龙16QS 上这个判据不成立。**

本机实测：

| 状态 | `0x07C3` | `0x0742` bit2 | `0x087F` 存储值 | 限充是否已写入固件 |
|---|---|---|---|---|
| 门控临时打开期间 | `0x04` | **1** | — | — |
| 恢复 `0x07C3 = 0x07` 之后 | `0x07` | **0** | **80** | ✅ 已写入 |

也就是说：**存储触发成功、存储值合法、限充已持久生效，但 bit2 依然是 0。**
本机的 bit2 只跟随 `state_is(4) || state_is(5)` 这个门控条件，**不跟随"存储值维持"这条路径**。

> ⚠️ **踩坑代价**：正因为如此，用上游的判据会得出"写入失败"的**假阴性**结论。
> 本项目按此判据排查了很久，直到经 WMI 邮箱直读 `0x087F` 才推翻结论。

**给其他机型适配者的建议**：不要用 `0x0742` bit2 判定成败。
要么经 WMI 邮箱直读 `0x087F`，要么用充电行为验证（放到上限以下再插电）。

## 2. 取消限充的实测（含两个代码缺陷）

用固件邮箱直读存储区，做完整的"取消 → 复核 → 重设 → 复核"：

```
起始      live=80  stored=80
取消后    live=0   stored=0    ← 存储区真的清零
重设后    live=80  stored=80   ← 重新写回
```

平台值每次恢复 `0x07`，身份字节 `0x0770` 始终 `0xFF`。8/8 检查通过。

排查过程中发现上游 `电池充电上限.pyw` 的 `_store_trigger()` 有**两个缺陷**：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 只校验平台值**恢复**成功，未校验 `0x07C3 = 0x04` **是否真的写进去** | 若写入未生效，门控其实没开、固件不会执行 `store_limit()`，但函数照旧报成功。取消限充时会出现 **`live` 清成 0 而 `stored` 仍留旧值** 的错配 |
| 2 | 写回原值时若抛异常，被外层 `except` 吞掉 | `0x07C3` **可能卡在 0x04（门控常开）**，无兜底恢复 |

本仓库的 `电池充电上限.pyw` 已修复：逐步回读校验 + `finally` 兜底，
并新增"启动时检测到 `0x07C3` 停在 4/5 就按出厂原值修复"。

## 3. WMI 邮箱读取：三个坑

本机实测可用的读取协议（与上游一致）：

```
读: Data = (0x0100 << 32) | addr   →  返回低字节即该地址的值
```

但有三个坑会让实现直接失败：

### 3.1 返回字段名是 `Return`，不是 `ReturnValue`

PowerShell 调用 `$obj.GetSetULong($data)` 返回 `ManagementBaseObject`，
**取值的属性名是 `Return`**。写成 `ReturnValue` 会静默取到 `$null`，
所有寄存器都读成 0 —— 看起来像"邮箱不响应"，实则字段名取错。

### 3.2 `AcpiTest_MULong` 有 **10 个实例**

```
ACPI\PNP0C14\1_0 … ACPI\PNP0C14\1_9
```

`Get-WmiObject -Class AcpiTest_MULong` 返回的是**数组**。
对数组直接调用方法会触发 PowerShell 的**成员枚举**，返回值变成 `Object[]`，
后续 `[uint64]` 转换报 `Cannot convert System.Object[] to System.UInt64`。

**必须只取一个实例**，例如 `@(Get-WmiObject ...)[0]`。
（实测 10 个实例读回的值相同，取哪个都行。）

### 3.3 PowerShell 5.1 的位运算与编码陷阱

- `([uint64]0x0100) -shl 32` 这类写法在 PS 5.1 上会把结果变成 `Object[]`。
  改用纯算术更稳：`[uint64]256 * [uint64]4294967296`。
- 中文 Windows 上 PowerShell 输出是 **GBK**。Python 侧用
  `subprocess.run(..., text=True)` 会按 UTF-8 解码 → `UnicodeDecodeError`。
  应捕获字节后自行容错解码（先 utf-8 再 gbk）。
- `.ps1` / `.cmd` 文件里**不要写非 ASCII 注释**：
  PS 5.1 按 GBK 读 UTF-8 文件会字节错位、吃掉换行符，
  把下一行代码并进注释 —— 表现为变量莫名其妙是 `$null`。

## 4. 持久性实测

| 场景 | 结果 |
|---|---|
| 写 `0x07B9 = 80` + 存储触发 | `0x087F` = 80（经邮箱直读确认） |
| **重启**（uptime 从 4957 分钟 → 6.7 分钟） | `0x087F` 仍为 **80**，`0x07B9` 仍为 **80** ✅ |
| 重启后 `0x07C3` | `0x07`（未改动） |
| 重启后 `0x0770` | `0xFF`（身份字节未动） |

即：**与上游结论一致，存储值跨重启持久，不需要后台程序或开机自启。**

## 5. 本机实测寄存器速查

| 地址 | 语义 | 本机实测 |
|---|---|---|
| `0x0740` | PROJECT_ID（低字节） | `0x10` |
| `0x0770` | ROM ID[0] | `0xFF` |
| `0x07A6` | 官方档位 bits[5:4]（0=长效 1=均衡 2=工作站） | `0x20` → 2 |
| `0x07B9` | 实时上限 bits[6:0]，bit7 = REACHED | `0x50`（80%） |
| `0x07C3` | 平台值 / 门控状态 | `0x07` |
| `0x0742` | bit2 = 门控条件成立（**非**存储维持） | 随 `0x07C3` 变化 |
| `0x087F` | **存储上限**（盲区，仅 WMI 邮箱可读） | `0x50`（80%） |

> 注：`test_restore` 实测表明**固件不会在运行时用存储值纠正实时上限**
> （把 `0x07B9` 写成 90，8 秒内保持 90 不变）。
> 因此"写个探针值看它弹回来"不能用作验证手段。

## 7. 复现步骤

```powershell
# 1) 只读探测（免管理员）：确认机型特征
py -3 tools\state_snapshot.py

# 2) 经固件邮箱直读存储区（需管理员）
tools\read-ec-wmi.cmd

# 3) 设置 / 取消上限（GUI，免管理员即可写入）
py 电池充电上限.pyw
```

管理员模式下的 GUI 会在每次写入后**自动经固件邮箱复核存储区**，
直接给出 `存储区复核：80% ✔` 这类确定结论。
