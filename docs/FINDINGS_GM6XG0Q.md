# 蛟龙16QS (GM6XG0Q) 适配与实测记录

本文件记录在**机械革命 蛟龙16QS** 上适配本项目时发现的新事实。
结论均在本机实测，与上游 [`docs/FINDINGS.md`](FINDINGS.md)（实测于无界15X）互补。

> ⚠️ **一句话结论**：本机固件**不会用存储值 `0x087F` 维持限充门控** ——
> 存储值能写入、也能跨重启持久，但限充**照样不工作**。
> 必须把门控 `0x07C3` **常驻钉在 `0x04`**，而该值重启即丢，所以**必须有开机重放**。

## 1. 核心差异：存储值**不能**维持门控

上游（无界15X）的结论是：让门控**短暂**成立一次，固件会把实时上限抄进存储区 `0x087F`，
**之后门控由存储值自行维持** —— 所以一次写入就永久生效，无需后台程序。

**本机不是这样。** 实测对照：

| 步骤 | `0x07C3` | `0x07B9` | `0x087F` | `0x0742` bit2 | 限充是否工作 |
|---|---|---|---|---|---|
| 初始 | `0x07` | `0x00` | — | 0 | ❌ |
| 写 `0x07B9 = 80` + 临时开门控 2.5s 后恢复 | `0x07` | `0x50` | **80** | **0** | **❌ 不工作** |
| **重启后**再读 | `0x07` | `0x50` | **80** | **0** | ❌ 不工作 |
| 把 `0x07C3` **钉住** `0x04` | `0x04` | `0x50` | 80 | **1** | ✅ **工作** |

也就是说：**存储值确实写进去了、也确实跨重启持久了**（这与上游一致），
但**本机固件不使用它来维持门控** —— 门控条件必须由 `0x07C3` 自身持续满足。

### 决定性证据：充电行为日志

电池放到 76% 后插电（`0x087F` 已为 80、`0x07B9` 已为 80）：

```
22:30:09  76%  插电
22:31:19  77%
22:32:29  78%
22:33:39  79%
22:34:49  80%   ← 到达上限
22:35:59  81%   ← 冲过去了，仍在充电（ec_current ≈ 1870）
```

**直接冲过 80%**，证明限充完全没生效。

随后把 `0x07C3` 钉成 `0x04`：

```
钉扎前   充电中   bit2=0   电流=1802
t=5s     未充电   bit2=1   电流=0     ← 立刻停充
t=60s    未充电   bit2=1   电流=0     电量始终 81%
```

**5 秒内停充、电流归零、电量卡住不动。**

### 由此得到两个结论

1. **`0x0742` bit2 是可靠的成效判据**（上游的说法在本机同样成立）。
   排查过程中曾一度认为"bit2 不反映存储维持路径"，那是**误判** ——
   真正的情况是：bit2 = 0 就代表控制环路没激活，限充根本没工作。
2. **本机必须走"门控钉扎"，不能走"存储触发"。**

## 2. 门控钉扎：可行，但易失，必须重复放

```
写 xram[0x07C3] = 0x04     # 门控条件恒成立
```

| 事项 | 实测结果 |
|---|---|
| 立即效果 | 5 秒内停充，`0x0742` bit2 = 1 |
| 固件常数 | **只认 `4`，不认 `5`**（写 5 能写进字节但门不开）—— 与 [losewayy](https://github.com/losewayy/uniwill-ec-charge-limit) 记录一致 |
| 身份字节 | `0x0770` 始终 `0xFF`，**从未改动** |
| **跨重启** | ❌ **丢失** —— 重启后 `0x07C3` 回到 `0x07`，门控关闭，限充失效 |
| 解决办法 | 开机重放（本项目提供 `pin_guard.py` 守护 + 启动项） |

对比一下本机两个寄存器的性质：

| 寄存器 | 语义 | 跨重启 | 能否维持限充 |
|---|---|---|---|
| `0x087F` | 存储上限 | ✅ **持久** | ❌ 本机固件不采信 |
| `0x07C3` | 平台值 / 门控 | ❌ **易失** | ✅ 采信，但得一直按住 |

**这张表就是本机适配的全部要害。**

## 3. 配套实现

| 文件 | 作用 |
|---|---|
| `电池充电上限.pyw` | 图形界面。应用限充 = 写 `0x07B9` + **钉住** `0x07C3`；取消 = 清 `0x07B9` + **释放** `0x07C3`。同时把"意图"写进 `setting.json` |
| `pin_guard.py` | 守护进程。每 30 秒读 `setting.json`，发现钉扎丢了就补上；取消限充时负责释放 |
| `install_autostart.py` | 在当前用户启动文件夹放一个静默 VBS 启动器（`--remove` 卸载，`--status` 查看） |

配置文件与心跳都在 `%LOCALAPPDATA%\MechrevoChargeLimit\`：
`setting.json` / `guard_heartbeat.json` / `guard.log`。
界面顶部会显示守护运行状态（读心跳 + **校验 PID 是否真的存活**，见第 9 节），并提供一键启停。

> ⚠️ **部署时注意安全软件**：往启动文件夹放东西会被火绒等国产安全软件拦（弹窗）。
> 必须放行，否则开机后守护起不来，限充会在重启后失效。

## 4. 取消限充：实测 + 发现的两个代码缺陷

用固件邮箱直读存储区，做完整的"取消 → 复核 → 重设 → 复核"：

```
起始      live=80  stored=80
取消后    live=0   stored=0    ← 存储区真的清零
重设后    live=80  stored=80   ← 重新写回
```

平台值每次都回到 `0x07`，身份字节始终 `0xFF`。8/8 检查通过。

排查中发现上游 `电池充电上限.pyw` 的 `_store_trigger()` 有**两个缺陷**：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 只校验平台值**恢复**成功，未校验 `0x07C3 = 0x04` **是否真的写进去** | 若写入未生效，门控其实没开、固件不会执行 `store_limit()`，但函数照旧报成功。取消限充时会出现 **`live` 清成 0 而 `stored` 仍留旧值** 的错配 |
| 2 | 写回原值时若抛异常，被外层 `except` 吞掉 | `0x07C3` **可能卡在 0x04（门控常开）**，无兜底恢复 |

本仓库的实现已改为逐步回读校验 + 异常兜底。

## 5. WMI 邮箱读取：三个坑

本机实测可用的读取协议（与上游一致）：

```
读: Data = (0x0100 << 32) | addr   →  返回低字节即该地址的值
```

但有三个坑会让实现直接失败：

### 5.1 返回字段名是 `Return`，不是 `ReturnValue`

`$obj.GetSetULong($data)` 返回 `ManagementBaseObject`，**取值的属性名是 `Return`**。
写成 `ReturnValue` 会静默取到 `$null`，所有寄存器都读成 0 ——
看起来像"邮箱不响应"，实则字段名取错。

### 5.2 `AcpiTest_MULong` 有 **10 个实例**

```
ACPI\PNP0C14\1_0 … ACPI\PNP0C14\1_9
```

`Get-WmiObject -Class AcpiTest_MULong` 返回的是**数组**，对数组直接调方法会触发
PowerShell 的**成员枚举**，返回值变成 `Object[]`，后续 `[uint64]` 转换报
`Cannot convert System.Object[] to System.UInt64`。

**必须只取一个实例**：`@(Get-WmiObject ...)[0]`。
（实测 10 个实例读回的值相同，取哪个都行。）

### 5.3 PowerShell 5.1 的位运算与编码陷阱

- `([uint64]0x0100) -shl 32` 在 PS 5.1 上会把结果变成 `Object[]`。
  改用纯算术：`[uint64]256 * [uint64]4294967296`。
- 中文 Windows 上 PowerShell 输出是 **GBK**。Python 侧 `subprocess.run(..., text=True)`
  会按 UTF-8 解码 → `UnicodeDecodeError`。应捕获字节后自行容错解码。
- `.ps1` / `.cmd` 里**不要写非 ASCII 注释**：PS 5.1 按 GBK 读 UTF-8 文件会字节错位、
  吃掉换行符，把下一行代码并进注释 —— 表现为变量莫名是 `$null`。

## 6. 本机实测寄存器速查

| 地址 | 语义 | 本机实测 |
|---|---|---|
| `0x0740` | PROJECT_ID（低字节） | `0x10` |
| `0x0770` | ROM ID[0] | `0xFF`（从未改动） |
| `0x07A6` | 官方档位 bits[5:4]（0=长效 1=均衡 2=工作站） | `0x20` → 2 |
| `0x07B9` | 实时上限 bits[6:0]，bit7 = REACHED | `0x50`（80%）；门控开时为 `0xD0` |
| `0x07C3` | 平台值 / 门控状态 | 出厂 `0x07`；钉扎时 `0x04` |
| `0x0742` | bit2 = **控制环路是否激活** | 钉扎前 0 / 钉扎后 1 |
| `0x087F` | **存储上限**（盲区，仅 WMI 邮箱可读） | `0x50`（80%，跨重启保持） |

> 补充：**固件不会在运行时用存储值纠正实时上限**。
> 把 `0x07B9` 写成 90，8 秒内保持 90 不变 ——
> 所以"写个探针值看它弹回来"不能用作验证手段。

## 7. 风险与已知边界

- **CVE-2026-64143** 只影响 ~2020 代 Uniwill 机型；本机 BIOS 为 2023-10-16，不在范围内，
  且已实测限充正常停充、温度/风扇无异常。
- 门控值 `4`/`5` 是**产品线标识值**，理论上按产品线分发的功能表可能走错分支。
  本机（与第三方在蛟龙16Pro 2025 上的实测）均**未观测到副作用**。
  另注：本方案改的是 `0x07C3`（平台值），**不碰** `0x0770`（ROM ID 身份字节）——
  后者被上游明确列为风险更高的一条路。
- 所有写入均为**易失 EC RAM**，不刷固件、不碰闪存，写回 `0x07` 即完全还原。

## 9. 守护进程的两个坑：假"运行中" 与 被连带结束

限充依赖守护在每次开机后重放钉扎，所以**守护必须真的活着**。
实际部署时踩到两个问题，都会让用户以为"一切正常"而其实限充已经没人管了。

### 9.1 心跳文件不能单独当存活判据（会误报"运行中"）

**现象**：界面显示 `限充守护：运行中 · 心跳 23:09:44`，但守护进程其实早已不存在。

**原因**：早期的 `guard_status()` 只比较心跳文件的时间戳：

```python
age = time.time() - hb["time"]
alive = age < max(90, interval * 3)      # ← 只看时间戳
```

守护被结束后，**心跳文件会留在磁盘上**，在 90 秒新鲜期内界面照样显示"运行中"，
按钮也仍是"停止守护"，点下去才报"停止失败"。

**修法**：同时校验心跳里的 PID 是否真的存在。

```python
h = kernel32.OpenProcess(SYNCHRONIZE, False, pid)
alive = kernel32.WaitForSingleObject(h, 0) == WAIT_TIMEOUT   # 0x00000102
```

两个细节：

- **`HANDLE` 是 64 位**，`OpenProcess.restype` 必须显式声明为 `c_void_p`，
  否则默认 `c_int` 会截断句柄。
- `OpenProcess` 返回 `ERROR_ACCESS_DENIED`(=5) 时**不能判定为已死** ——
  守护若以更高权限运行（例如提权启动），普通权限的界面无权查询它。
  这种情况要回退到"只看心跳时间戳"，否则会误报"未运行"。

判定改为 `(pid_ok is not False) and fresh`：PID 已确定退出 → 立即显示未运行；
无法判定 → 交给时间戳兜底。

### 9.2 守护可能被调用方的 Job 对象连带清理

**现象**：点「启动守护」后日志有 `guard started`、心跳也写过一次，
但几十秒后再看，进程已经不在了，且事件日志里**没有任何崩溃记录**。

**排查**：把守护放在前台连续跑（6 秒间隔，2 分钟）完全稳定、0 异常 ——
**代码本身不崩**。结合"进程在父 GUI 退出前后消失"，指向 Job 对象的连带清理：
用 `DETACHED_PROCESS` 只能脱离控制台，**并不能脱离 Job**。
GUI 点「以管理员身份重启」时会 `self.destroy()` 并退出，旧实例若处在某个 Job 里，
它的子进程会被一并结束。

**修法**：启动守护时优先加 `CREATE_BREAKAWAY_FROM_JOB`，失败则自动降级：

```python
for extra in (CREATE_BREAKAWAY_FROM_JOB, 0):
    try:
        subprocess.Popen(..., creationflags=base | extra)
        return True, None
    except OSError as exc:
        last = exc
```

Job 不允许脱离时 `CreateProcess` 会直接失败，捕获后去掉该标志重试即可。

### 9.3 顺带做的两处加固

| 加固 | 说明 |
|---|---|
| 守护主循环整体包 `try` | 原来只有 EC 操作那段有异常保护；驱动报错、编码问题、文件占用等意外会让进程**静默退出**。现在任何意外都只记一行日志，循环继续 |
| 界面打开时自愈 | 若 `setting.json` 的 `enabled=True` 但守护没在跑，启动 GUI 时自动补一次 —— 覆盖"被安全软件拦掉、开机自启没生效"等情况。`enabled=False`（已取消限充）时不拉起，尊重用户意图 |

### 9.4 一句话部署结论

> 守护能不能长活，取决于**三层**：脱离 Job（9.2）、不被安全软件拦（第 3 节），
> 以及界面打开时的自愈兜底（9.3）。
> 判断守护是否真的活着，**必须看 PID，不能只看心跳文件**（9.1）。

## 10. 存储值 `0x087F` 与实时上限 `0x07B9` 是强耦合的（实测）

有人会想：既然本机固件**不采信**存储值，那能不能把它清成 0，只留钉扎？

**答案是：不能。** 实测数据（`tools/clear_stored_limit.py`，需管理员）：

```
初始                 stored=80   live=80   platform=0x04   gate bit2=1
live=0 + 门控打开     stored=0    live=0    platform=0x04   ← 固件把 live 抄进了存储区
门控关闭             stored=0    live=0    platform=0x07    ← 门控关着时它保持不变
live=80 + 门控钉扎    stored=80   live=80   platform=0x04    ← 2 秒内就被同步回去
```

### 机制

固件的逻辑是**电平触发**的：只要门控条件成立（`0x07C3 == 4/5`），
且 `live_limit != stored_limit`，它就把 `live` 写进 `stored`，约 2 秒内完成。
门控一关就停止写。

### 推论

- **存储值不是"残留垃圾"，而是固件强制的镜像。** 只要限充在正常工作
  （门控钉扎），`stored` 必然等于 `live`。
- 想让它保持为 0，**唯一的办法是不放钉扎** —— 也就是取消限充。
  所以「清空存储值」与「限充生效」在本机型上互斥。
- 实践上**不需要管它**：它不影响任何行为，而且万一将来 BIOS 更新让固件
  开始采信存储值，它已经等于当前设定，反而正好。

### 附带确认：驱动通道读不到这个地址

```
0x07B9 -> 0xD0     (正常)
0x07C3 -> 0x04     (正常)
0x087F -> 0xFF     ← 盲区，返回的是假值
0x0880 -> 0xFF     ← 同样
```

`0x087F` 落在 H2RAM 盲区，驱动程序读它只会稳定返回 `0xFF`。
要读真值只有固件 WMI 邮箱一条路，而它**必须管理员** —— 这也是为什么
本项目的"复核存储值"功能只在管理员模式下出现。
